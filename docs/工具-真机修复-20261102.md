# 工具真机修复：平板无 panelNav、导出通道、abort 复位（2026-11-02）

> 对象：`dsh-adapt-packs/tools/device-verify/`（v2 → v2.1）
> 设备：Xiaomi Pad 9 Pro Max（`M367FC`，序列号 `0983986009983540`）· Android 17 · WebView 150.0.7871.181 · App 0.7.1 · dsh-mobile **0.8.1**
> 视口：竖屏 **909×1314**（≥900 ⇒ 宽布局）· 横屏 1363×860 · DPR 2.5
> 截图目录：`.cache/device-verify/0983986009983540/<时间戳>/`

## 1. 结论

| 问题 | 修复 | 真机结果 |
| --- | --- | --- |
| 平板 ≥900px 时宿主不渲染 `.dshm-panelNav`，工具只会点返回栏 → `panel-not-closed` → 整轮 ABORT | 关闭改成 5 条策略链，核心是派发宿主自己的 `dsh-mobile:native-back` 事件 | 四个场景一次跑完，每个都 `close=native-back-event`，无 ABORT |
| sink POST 在 https 页面被混合内容拦截；logcat 在本机根本不转发 console | 报告里写死三条通道的真实可用性，新增 `channels` 命令与 `--channel screenshot`，`run` 在真机上自动落到截图通道 | `sink=failed:fetch logcat=sent` 但 `adb logcat` 里 `[dsh-verify]` **0 行**；截图通道给出完整读数 |
| 中止后面板停在错误状态，下一次 reload 前页面不可用 | `cleanup()`：恢复 `data-dsh-adapt`、关闭残留面板、收起抽屉，结果写进 `report.cleanup` | 结束时 `panel=0/closed`、`cleanup ok=true panelOpen=false` |
| （顺带暴露）同一插件面板两次跑出 `n=7` / `n=13` / `n=94` | 稳定签名加入**面板文本长度**、`settleWindowMs=2000`、稳定后再 400ms 复核、opt-out 回程后若控件数变了就**重测一次** | 同一个 context-insights 面板从 13 回到 127；随后多次运行稳定在 `127 / 446 / 94 / 11` |

## 2. 现象（修复前）

旧 v2 构建在平板上跑完第一个场景就停在：

```
phase=done shell=1 drawer=rail panel=1/open off=- ovf=0
FAIL context-insights: n=13 min=44 <44=0 hit=12/13 opt=<44=115 flo=1 ovf=0 2148ms
   ↳ panel-not-closed: 面板没关回去，后续场景会在错误的面板上测量。
   ↳ clicked 上下文洞察
export title=full 2623B sink=failed:fetch logcat=sent ABORT=panel-not-closed
```

根因有两层：

1. **面板关闭**：`closePanel()` 只找 `.dshm-panelNav` 的返回按钮；0.8.1 在宽布局下根本不渲染这个返回栏
   （`lib/mobile-layout.js:680`：`state.panelInfo.activePanelId !== null && !wideViewport ? …panelNav… : null`），
   于是 `no-back-button` → 失败 → 中止。
2. **取数**：真机页面是 `https://192.168.1.11:3443`，sink 是 `http://127.0.0.1:8799`，WebView 按混合内容拦截；
   logcat 通道虽然「发出去了」，但 App 没有把 WebView console 转进 logcat，所以 `adb logcat` 一条也抓不到。

## 3. 改法

### 3.1 关闭面板：五条策略 + 逐条轮询确认

`overlay-lib.js` 新增纯函数 `planClose(facts)` 决定顺序，`overlay.js` 的 `closeStrategies()` 提供执行体；
每条策略执行后都轮询 `.dshm-main[data-dsh-panel]`（0.8.0 没有该属性时退回 `.dshm-panelNav` 是否存在），
超时 `closeTimeoutMs`（默认 1200ms）再换下一条：

| 顺序 | 策略 | 何时可用 | 为什么 |
| --- | --- | --- | --- |
| 1 | `panelNav-back` | 存在返回栏且按钮未 disabled | 窄屏（<900px）的正常路径 |
| 2 | `native-back-event` | 总是尝试 | 0.8.1 `lib/mobile-layout.js:792` 定义 `onNativeBack`，`:806` 在 `window` 上监听 `dsh-mobile:native-back`，处理逻辑里 `controller.selectPanel(null)` —— **平板唯一可用路径** |
| 3 | `sidebar-toggle` | 侧栏能找到同名入口 | 再点一次同一个入口 |
| 4 | `escape-key` | 总是尝试 | 在 document 与 window 上派发 `Escape` |
| 5 | `history-back` | `allowHistoryBack` 且 `history.length > 1` | 最后手段，可能翻页，默认允许但可关 |

- `data-dsh-panel` 从 `1 → 0` 才算成功；成功那条写进 `scenario.detail.close.strategy`，全部尝试写进 `detail.close.attempts`。
- 覆盖层每行显示 `close=<策略>`，所以**截图本身就是证据**（见 §4）。
- 关闭失败不再中止整轮：该场景记 `panel-not-closeable` 并执行 `cleanup()`，后面场景继续，
  这样一次运行仍能拿到其余场景的独立结果。
- 新增原因码 `panel-not-closeable`、`native-back-unhandled`；旧 `panel-not-closed` 保留只为解析历史报告。

### 3.2 收尾复位：`cleanup()`

每次运行结束（成功、失败、异常）都执行一次并写入报告：

```jsonc
"cleanup": {
  "ok": true, "cause": "end-of-run",
  "panelOpen": false, "drawerOpen": false, "optOutRestored": true,
  "attempted": [{ "step": "close-panel", "ok": true, "strategy": "native-back-event" }]
}
```

三件事：把 `html[data-dsh-adapt]` 恢复成**开跑前的值**（不是无脑删除）、用同一条策略链关掉残留面板、
收起我们打开过的抽屉。`ok` 三项全达成才为 `true`。异常路径（`overlay-error`）与 `page-not-loaded` 也会先 cleanup 再写报告。

### 3.3 导出通道：不再假装 logcat 能用

- `run.mjs report` 开场打印通道预检：`gateway: https://…`、`sink …`，并在 https + `http://127.0.0.1` 组合时直接点名
  「WebView 会按混合内容拦掉这条」。
- 新增 `run.mjs channels`：一次说清 sink / logcat / screenshot / title 四条的当前可用性和依据。
- 新增 `--channel screenshot [--wait N]`：等 pilot 跑完就截图，并打印「读覆盖层顶部面板」的字段说明。
- `run --reload` 在真机上自动切到 screenshot 通道，不会干等 180 秒超时。
- 失败信息重写：logcat 行数为 0 时明确写「本机 App 没有转发 console，请用截图通道」。
- 覆盖层导出行在 sink 失败时多打一行 `hint: 真机取数用截图（sink 需 HTTPS/同源端点；logcat 取决于 App 是否转发 console）`。

### 3.4 顺带修：面板内容「假稳定」

真机上同一个插件面板在不同次运行里跑出过 `n=7`、`n=13`、`n=94`、`n=127`。原因不是抖动，而是**面板数据还没到**：
骨架屏/空态本身就「稳定」，只看控件尺寸判断不出来。四处改动：

1. **签名加入文本长度**（`overlay-lib.panelSignature`）：控件尺寸签名 + `innerText` 长度（40 字符一桶）。
   骨架 → 内容时控件数可能不动，但文字量会跳变 —— 实测 context-insights 因此从 13 回到 **127**；
2. `settleWindowMs` 仓库配置从 900 → **2000**；
3. 稳定后再等 **400ms** 复核签名，变了就重新等（最多 3 次）；
4. `opt-out` 回程（约 1–3s）结束后再量一次控件数；变了就重新 settle + 重测，并在 `detail.remeasured` 标记。

加固后连续运行：`127 / 446 / 94 / 11` 稳定复现（见 §4）。

### 3.5 `reload` 改为真正的重载

WebView 没有地址栏；`input swipe` 的下拉手势在平板上会落进 composer 并弹出软键盘（实测把 `innerHeight` 从 860 压到 441）。
`reload` 默认改成 `am force-stop` + launcher 重启 App（页面重新加载、pilot 重跑），保留 `--gesture` 给下拉刷新可用的设备。

## 6. 仍然存在的限制

1. **sink 在真机上仍然不能用**：需要 HTTPS 端点或与页面同源的地址；本轮没有为此新增代理。真机取数只能靠截图。
2. **「数据未到」只能缓解、不能根治**：文本签名 + 重测能抓住大多数骨架屏，但如果某个面板的数据比 `settleWindowMs`
   更晚到（慢网/慢接口），仍会量到空态；报告会给出 `detail.remeasured` 与 `ms`，请结合多次运行判断。
3. **logcat 通道在本机不可用**：取决于 App 的 `WebChromeClient.onConsoleMessage` 是否转发；本机（Pad 9 Pro Max / Android 17 / WebView 150）实测 0 行。
4. **title 通道只有浏览器能读**：adb 没有 CDP，也没有取标题的命令。
5. **剪贴板通道不存在**：Android 17 上 `cmd clipboard` 返回 `No shell command implementation`，`Copy JSON` 只能人工长按。
6. **`keyboardProbe` 在平板上测不到键盘**：程序化 focus 不弹 IME；要测键盘得用真实点击（本轮用 `input tap` 得到 419px 的一次观测）。
7. **横屏本轮没有重跑完整场景**：横屏 1363×860 也 ≥900，理论上与竖屏同一路径（无 panelNav），但只做了键盘观测，没有重跑四场景。
8. **关闭策略第 2 条依赖宿主事件名**：`dsh-mobile:native-back` 是 0.8.1 的实现细节（不是公开 API）；上游改名时要同步改 `closeStrategies()`，
   单测里 `planClose` 的断言会提醒顺序，但改名本身无法自动发现。
9. **opt-out 属性在 App 内不可注入**：本轮测量里的 `opt=<44=…` 是覆盖层自己切换 `html[data-dsh-adapt=off]` 得到的，能生效；
   但「用装/不装扩展来对照」的老方法仍然只能用重装插件模拟。
